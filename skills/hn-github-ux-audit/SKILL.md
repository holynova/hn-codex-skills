# HN GitHub 体验审计

把一组 GitHub 项目当成给普通人用的产品来审：不懂技术的小白拿到它，能不能不用说明书走完主链路、拿到他想要的东西。审完直接修，修完验证过再交付，修复一律走分支加未合并 PR，等用户人工审核后按编号批量合并。

本技能沉淀自 2026-11-14 的一次实战：95 个项目、1,586 处修复、65 个 PR。标准原文见下方「十条审计标准」，一字不改；工作流与硬规则是那次实战验证过的做法。

## 适用场景

- 批量审核：用户指定最近 N 个项目、或作品集里的一批项目。
- 单站审计：只审一个仓库时同样走完整流程，只是跳过分组与汇总。
- 审计加修复是默认：用户说“审核”即包含修复；只出结论不出修复时用户会明说“只审不修”。
- 只审体验设计，不审代码架构、性能、安全（除非问题直接堵住主链路）。

## 十条审计标准（用户原文）

逐站逐项核对，记录时按标准编号归类。编号沿用实战中的归类法（文案克制归入标准 1，三方案机制为标准 10），与 2026-11-14 的 95 份审计记录一致。

1. **小白主链路**：把自己当做一个普通不懂技术的小白，他拿到我们产品，能否把主链路走完产出他所需要的东西，哪些地方有卡点，哪些地方没有讲明白，哪些地方的衔接不通顺，全部去修复，让用户不用说明书也可以完成产品的使用，假如实在不能，可以适当补充提示说明。产品上能用产品本身表达清楚的地方就不要再加文案说明，不要啰嗦的解释一个东西，仔细思考每一个说明文案是否达意且不啰嗦，交互视觉可以说清楚的地方就不要用文案再表达一遍。
2. **文案本地化**：所有文案需要符合对应语言当地人的使用习惯，需要仔细斟酌词藻，不要干巴巴的翻译，可以从 Apple、Windows 系统以及知名网站去找同类词的最好翻译和解释，文案做到尽可能让本地人感觉非常简单、易懂、清晰。
3. **数字**：在数字的表达上需要让用户明白这个数据指的内容，以及考虑到数据表达意思后的易读，比如钱、指标、距离各种单位需要考虑到本身的最佳实践，数据的准确性非常重要，不要为了偷懒少了数据的校验。
4. **确认弹窗**：对于用户确定的操作不需要反复找用户确定，只有在会产生不可逆影响的时候二次找用户确定是否需要执行，防止满屏都是各种弹框确定，对于危险的操作不要出现大片的红，需要考虑用户操作一个产品的愉悦度，用户不是傻子不要过度担心会犯错。
5. **视觉**：一个页面只留一个强调色，尽量不要使用橙色、陶土色和后台常见的那种老企业亮蓝色，灰色全部用偏暖的灰，不使用冷冰冰的蓝灰，找不到合适的颜色可以去中国传统颜色里面去找到合适的。
6. **字号**：字号类型尽可能少一点，一个页面最多控制 4 种不同的字号，需要考虑到页面整体的阅读节奏感，清晰感以及文字的对比度，确保符合无障碍，包括考虑到行间距、字间距、段落间距需要反复调整，同时保持整体的规范一致。
7. **字体与符号**：少用斜体、等宽字体、全大写，要用的场景必须要有详细的理由说明，说明文案不要使用斜体，等宽字体只用于代码、路径、指标，按钮和标签里面的字不要大写，少用中间点 · 来连接内容。同一个动作在整个产品里面只用一个动词，此外动词的考虑尽量不要催促用户去执行，比如少用立即购买这种营销词。
8. **设计规范**：页面的按钮、间距、圆角、分割线、弹窗、动画、阴影这类设计规范保持一致，同时保持克制，不打扰用户，嵌套的圆角要同心，里面的圆角等于外面的圆角减去间距会更好看。页面默认是平的，不叠阴影、不发光、不加毛玻璃，阴影只给真正浮起来的弹窗，不要卡片套卡片。
9. **多语言与响应式**：在多语言的环境下，优先考虑最长文案的排布，优先考虑达意而非为了好看而改变原意，可以改文案，但不要变字号和截断。需要特别考虑在不同尺寸下的展示效果是否都良好，考虑到用户常用的设备，全部去测试，遇到不好的地方全部修复。
10. **三方案机制**：对于反复调整不好的设计，或者做了好多轮都感觉不好看的设计，让 Agent 帮你出 3 个他认为最好的方案来让你挑选，然后你选择一个更好的，告诉他去优化，直到改到你满意，我比较喜欢让 AI 生成对比前后的图片放到一个 pdf 里面，这样我的阅读对比体验会更好。

## 工作流

### 1. 定范围与编号

- 按创建时间倒序拉取仓库清单（GitHub API `created desc`），按此顺序全局编号 #1、#2……编号一旦确定不再重排，后续 PR 标题、记录、报告全部带编号。
- **只审作品集里的作品**：以作品集数据（`https://xiaosang.cc/data/repos.json`）为准，按仓库 URL 过滤；不在作品集内的列出并说明原因，不审、不修、不推。
- 先报范围清单给用户确认：共多少个、排除哪几个（及原因）、编号起止。用户确认后再动手。

### 2. 分组并行（批量时）

- 10 个以上分多组并行，每组 8–13 站；设一个协调员汇总核验，各组执行员只负责自己组内的站。
- 每组交付：逐站记录（见 `references/audit-record-template.md`）、修复分支与 PR 链接、每站一句话结论。
- 协调员汇总前逐组核验：PR 是否 open 未合并、默认分支 HEAD 是否未动、记录是否齐全。

### 3. 逐站审计

- 克隆仓库到本地运行，亲手走一遍主链路：从入口到产出，每一步记下卡点、讲不明白、衔接不顺的地方。
- **大仓库禁全量克隆**：100MB 以上的仓库一律 sparse checkout 或只取单个文件（如图片库类仓库可达数 GB）。
- 数字逐项校验：页面上每个数字都要找到代码或数据源核对，错了就改，改不了就删；绝不为了省事跳过校验。
- 非网页项目（浏览器扩展、命令行工具、本地脚本）只审说明文档与首次使用流程，不硬套网页视觉标准。
- 跳转页、纯展示页轻审：只核对跳转目标、文案与数字。
- **定型风格不推翻**：用户明确要求过的风格（像素风、幻想/复古游戏 UI、品牌色）只修链路与文案，不动风格本身；游戏内的语义色（如阵营红蓝）、拟物装饰属于游戏语义，保留。

### 4. 修复

- 按标准逐项修，修一处记一处：问题证据、改法、改动位置（文件与行号）。
- 能用产品本身表达就不用文案；必须补说明时一句话讲清，不啰嗦。
- 修完先在本地验证（见第 5 步），验证通过才提交；验证不过不推。

### 5. 验证（交付铁律）

- **做完任何东西必须自己先测试再交付，没有测试结果就不交付**：构建通过、改动逻辑实测、数字逐项核对、截图抽查。
- 响应式与实际游玩没有真机时只做代码检查，并如实记录“未真机验证”，不得声称验证过。
- 截图对比：改前拍线上旧版，改后拍本地修复版，同一页面、同一范围；差异要在图里看得见。

### 6. 提交与 PR（禁止直接发布）

- 修复一律推到审计分支 `audit-YYYY-MM`（如 `audit-2026-11`），再开 PR，**保持未合并**，等用户人工审核后按编号批量通知才合并。
- PR 标题带编号，格式：`#<编号> 审计修复：<仓库名>（<修复数> 处）`；正文列出主要修复与遗留决策。
- 推送前后都要核对默认分支 HEAD 未变；默认分支零触碰是硬要求。
- 合并后生效方式要在 PR 正文写明：GitHub Pages 站合完自动生效；Cloudflare Worker 站合完仍需重部署。

### 7. 汇总报告

- 写一份汇总 `REPORT.md`：总数口径、按标准分的修复数、每站一句话结论、真问题示例、待用户决策清单（逐项编号）。
- 计数口径写清楚：按“组”还是按“处”，跨标准重复计数时注明差额原因。
- 待决策事项单独列出，不要藏在正文里；需要用户手动操作的（如改 workflow、换 token）写明具体步骤。

### 8. 前后对比报告（用户要求时）

- 每站 5 项：违反了什么规则、改动方案、改了哪些、前后对比、现在的状态；说人话，术语首次出现加括号解释。
- 对比图左右并排（左改前、右改后），整页截图，点开放大可切换；图注写清差异点与来源。
- 无界面可截的站用示意还原（按真实数值绘制并标注）或数值对照表，原因写在站内。
- 站数多、图片大时不要做单文件 HTML（95 站约 190 张图会超 40MB）：做图片独立文件、按需懒加载的网页版。细则见 `references/before-after-report.md`。

## 三方案机制

反复调整不好、做了好多轮都感觉不好看的设计：出 3 个最好的方案，前后对比图放进一个 PDF，让用户挑；用户选定后再优化，直到满意。没有一站到这个程度时不强行出 PDF，如实说明即可。

## 输出

- 逐站记录：`references/audit-record-template.md`。
- 汇总报告：总数、按标准分布、每站一句话、待决策清单。
- 给用户的汇报：简洁干练，短句加 bullet，先给结论再给细节；修了多少处、几个 PR、哪些待他定。
- 审计中发现的新问题（包括审计本身引入的回归，如改后排版重叠、按钮出屏）要如实写进记录与图注，不擅自二次修改，等用户定是否回修。
