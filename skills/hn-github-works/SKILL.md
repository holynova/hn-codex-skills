# HN GitHub 作品集生成器开发

## 目标

在当前工作区交付可运行、可维护的“CLI 采集器 + 静态作品站”MVP。扫描 GitHub 仓库和公开部署，保留来源与失败状态，生成可人工校对的数据，再导出无需后端即可浏览的作品集。

## 职责边界

- 仅处理作品集生成器本身的开发、扩展和修复。
- 如果用户只要求发布一个已有项目，使用 `hn-project-publisher`。
- 如果用户已有完整数据，只要求生成通用静态图库，使用 `hn-data-to-github-pages-gallery`。
- 如果任务只是普通前端打磨或交付，使用 `hn-frontend-project-shipper`。
- 不主动加入账号体系、付费、多人协作、复杂后台或数据库服务。
- 未经用户明确要求，不提交、推送、发布或修改远端仓库。

## 工作原则

- 先检查工作区，再给出简短实施计划；读取项目说明、源码结构、包管理器、脚本、Git 状态和现有约定，保护无关改动。
- 优先复用现有技术栈和组件。绿地项目可默认采用 Node.js CLI、GitHub API、Playwright 和依赖较少的静态站方案，但不要为了“技术建议”重写已有架构。
- 实现真实数据流和主要交互，不交付仅有静态卡片或硬编码演示数据的页面。
- 把外部数据视为不可信输入。校验 URL、文件路径、HTML/Markdown 和图片；渲染摘要时转义内容，截图前默认拒绝本机、私网、链路本地及非 HTTP(S) 地址。
- GitHub token 仅从环境变量或已登录 CLI 获取，使用完成任务所需的最小只读权限；不要写入配置、日志、缓存、README 或构建产物。
- 自动摘要、标签和分类必须保留来源并标记为待校对。人工修改存入独立的策展数据，不得在再次扫描时被覆盖。
- 所有生成文件使用临时文件加原子替换；删除旧截图、缓存或导出目录前必须显示范围，并取得用户确认或提供可恢复备份。

## 实施流程

1. **理解现状并确定最小切片。**
   - 检查入口、数据目录、构建方式、测试、README、Git 状态和可复用模块。
   - 明确本轮是新建 MVP、补齐缺失功能还是修复现有流程。
   - 用 3–7 个步骤给出简短计划，再开始编辑。

2. **固定产品契约。**
   - 开始建模前阅读 `references/mvp-contract.md`。
   - 使用稳定 ID 关联 `repository`、`deployment`、`screenshot`、`tag` 和 `curation`。
   - 分离扫描生成数据、人工策展数据、缓存和最终导出，确保重新扫描不会丢失人工修改。
   - 明确定义成功、空结果、部分成功、限流、不可访问页面、截图失败和摘要待复核状态。

3. **实现仓库采集。**
   - 支持 GitHub 用户名或个人主页 URL；需要组织扫描时显式选择 owner 类型。
   - 正确处理分页。默认排除 fork 和 archived 仓库，并让过滤规则可配置。
   - 获取仓库元数据、topics、主要语言、homepage 和 README。标准 README 接口返回 404 时，允许在仓库根目录查找 `README*` 作为回退。
   - 提供有界并发、缓存 TTL、请求间隔、速率限制感知重试、超时、进度序号和 debug 日志。日志写清每个仓库被保留或跳过的原因。
   - 公共仓库可无 token 运行；私有仓库或更高配额必须由用户明确提供已授权的只读凭据。

4. **检测并验证部署。**
   - 从仓库 homepage、GitHub Pages 元数据和可预测 Pages 地址生成候选 URL，同时记录发现来源。
   - 对候选地址执行带超时、重定向限制和响应大小限制的 HTTP(S) 验证；不要把仅能拼出的 URL 当作在线部署。
   - 将 `verified`、`unreachable`、`invalid_url`、`skipped` 等状态写入数据，保留最后检查时间和可读错误原因。

5. **截图、摘要和分类。**
   - 仅对已验证且通过网络边界检查的公开页面运行 Playwright。设置固定视口、导航超时、有限重试和稳定输出路径。
   - 截图失败不得阻断其他项目；记录失败状态，并允许人工指定已有图片或稍后重试。
   - README 摘要优先采用可追溯的抽取式规则；如使用模型生成，明确标为自动建议，不虚构功能、用户量或运行状态。
   - 从 topics、语言、依赖和 README 生成候选标签与类别，保留规则来源；人工修改优先于自动结果。

6. **提供人工校对。**
   - 提供可编辑的策展文件或本地校对界面，至少支持隐藏、置顶、顺序、标题、摘要、类别、标签、部署地址和截图覆盖。
   - 写入前展示变更，校验未知仓库 ID、重复顺序和无效路径；保留最后一次有效文件或备份。
   - 支持“重新扫描 → 合并策展覆盖 → 重新导出”，并用测试证明人工内容不会丢失。

7. **导出静态作品站。**
   - 输出自包含或路径稳定的静态资源与规范化数据，不要求运行时后端。
   - 展示项目标题、摘要、仓库链接、已验证在线地址、截图、技术标签和人工置顶顺序。
   - 实现有意义的搜索、分类或标签筛选，并覆盖无仓库、无在线页、无截图、部分失败和空筛选结果。
   - 对外部链接使用安全属性，对动态文本进行转义；不得把 token、绝对本地路径、调试日志或原始敏感数据导出。

8. **验证并交付。**
   - 为 URL 安全检查、分页、README 回退、缓存、限流重试、策展合并、排序和静态导出补单元测试。
   - 使用 fixtures 或 mock 测 GitHub API，不把实时网络和个人 token 作为默认测试前提。
   - 对截图流程至少运行一个本地页面集成测试；对静态站运行构建、浏览器核心流程和移动端检查。
   - 运行项目已有的 test、lint、typecheck 和 build，修复本次改动造成的问题。
   - 更新目标项目的 README，写明启动方式、授权范围、命令示例、功能范围、技术选择、数据目录、已知限制和下一步。

## 完成标准

- 从一个测试用户或 fixture 扫描出规范化仓库数据，并能在无 token 的公共模式运行。
- 已验证部署才进入默认截图队列；截图失败和限流不会让整批任务丢失。
- 人工置顶、隐藏和文案覆盖在再次扫描后保持不变。
- 静态站使用真实生成数据，支持核心浏览与空状态，并能在本地构建和打开。
- 自动判断可追溯，权限边界清晰，生成物不含密钥或本机绝对路径。
- README 和测试与实际实现一致。

## 交付格式

```text
完成：
- 功能与主要交互

验证：
- 测试、构建和浏览器检查

文件：
- 关键代码、数据模型、配置和 README

尚未解决：
- 限制、失败项目和下一步

Git 状态：
- 未提交 / 已按用户要求提交
```
